# Synthetic Incident Dataset

20 synthetic incident scenarios, generated by `generate_dataset.py`
(stdlib-only, deterministic per-scenario seeding — re-running it reproduces
byte-identical output).

## Directory layout

```
data/incidents/
├── _index.json            # id, slug, category, difficulty, services, flags for every scenario
└── INC-0NN/
    ├── meta.json           # non-spoiler: incident id, services, time window, available metrics
    ├── logs.log             # synthetic log lines — the "log store" (Log Agent reads this, Stage 6)
    ├── metrics.json          # synthetic time series — the "metrics store" (Metrics Agent reads this, Stage 6)
    └── deploys.json           # synthetic deploy history — the "deploy-history store" (Deploy-History Agent reads this, Stage 6)
```

```
eval/
├── gold/INC-0NN.json      # gold root cause + evidence + remediation + risk tier, per scenario
├── gold_set.md             # human-readable summary table (generated — see generate_gold_set_md.py)
└── rubric.md                # scoring rubric used to grade an agent's diagnosis against gold
```

## Why gold answers live outside `data/incidents/`

From Stage 3 onward, agents are given read access to `data/incidents/<id>/`
(logs, metrics, deploys) to diagnose the incident. **The gold answer is
never written anywhere under `data/incidents/`.** This is a deliberate
eval-integrity decision, not an oversight — it means a future agent with
broad filesystem read access (e.g. an MCP filesystem server in Stage 13+)
still can't accidentally read its own answer key. `generate_dataset.py`'s
validation step (see below) checks for this on every regeneration.

## Schema reference

**`meta.json`**
```json
{
  "incident_id": "INC-005",
  "alert_name": "Alert: anomalous behavior detected — checkout-api, orders-db",
  "services": ["checkout-api", "orders-db"],
  "window_start": "2026-03-01T00:00:00+00:00",
  "window_end": "2026-03-01T01:30:00+00:00",
  "available_metrics": ["db_pool_active", "db_pool_waiting"],
  "note": "..."
}
```

**`logs.log`** — one line per log entry, space-delimited fields, sorted by
timestamp:
```
2026-03-01T00:43:40+00:00 service=checkout-api level=ERROR msg="db connection pool exhausted: active=50 idle=0 waiting=213"
```

**`metrics.json`** — one key per metric name, each a list of `{ts, value}`
points at 1-minute resolution:
```json
{
  "db_pool_active": [
    {"ts": "2026-03-01T00:00:00+00:00", "value": 14.84},
    ...
  ]
}
```

**`deploys.json`** — chronological list of deploy/change events (may be
empty; may include events unrelated to the incident — see distractor
scenarios):
```json
[
  {
    "deploy_id": "deploy-001",
    "timestamp": "2026-02-28T23:45:00+00:00",
    "service": "marketing-site",
    "version": "1.4.2",
    "description": "marketing-site: unrelated homepage banner update"
  }
]
```

**`eval/gold/INC-0NN.json`** — see `eval/rubric.md` for how each field is
used to score an agent's output. Key fields: `root_cause`, `evidence`,
`recommended_remediation`, `remediation_risk_tier` (cross-references
`openspec/risk-classification.md`), `is_false_alarm`, `recurrence_of`,
`distractor_note`, `primary_stage_use`.

## Coverage

- **20 scenarios**, 19 distinct categories (one category, `memory_leak`,
  appears twice by design — see recurrence pair below), difficulty split
  5 easy / 10 medium / 5 hard.
- **2 distractor pairs** (INC-005/INC-018, INC-007/INC-017) — scenarios
  that produce similar surface symptoms but have different root causes and
  different distinguishing signals in the data. These exist to give the
  Stage 8 debate mechanism and Stage 9 Tree-of-Thought hypothesis
  branching something real to adjudicate, and to produce the
  before/after false-positive-rate comparison ROADMAP.md calls for.
- **1 false-alarm scenario** (INC-019) — no real anomaly exists; tests
  that agents don't hallucinate a root cause under pressure to produce one.
- **1 recurrence pair** (INC-002 → INC-020) — the same underlying bug
  pattern on a different service, for measuring the Stage 12 episodic
  memory / self-improvement loop's "second encounter" improvement.
- Every scenario is tagged `primary_stage_use` indicating which later
  roadmap stages it's specifically designed to exercise (see
  `eval/gold_set.md` for the full table).

## Regenerating

```bash
python3 generate_dataset.py          # from within data/
python3 eval/generate_gold_set_md.py  # from the repo root, after
```

Both scripts are deterministic (seeded per-scenario by incident id +
slug), so regenerating without editing `SCENARIOS` in
`generate_dataset.py` produces byte-identical output.

## Adding a new scenario

Per the OpenSpec workflow (see `openspec/README.md`), adding a 21st+
scenario should go through a proposal amendment, not a silent edit:

1. Add an entry to `TEMPLATES` if it's a new category, or reuse an
   existing one.
2. Add a `dict(...)` entry to `SCENARIOS` in `generate_dataset.py`,
   including a `gold` block with `root_cause`, `evidence`,
   `recommended_remediation`, `remediation_risk_tier` (classified per
   `openspec/risk-classification.md`), and `risk_rationale`.
3. Re-run both generator scripts.
4. Re-run the validation checks (leakage, false-alarm cleanliness,
   non-empty metrics) documented in the Stage 1 OpenSpec proposal's
   acceptance criteria before committing.
